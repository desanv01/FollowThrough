Adopted 7 November 2026 after the user asked main to consult the actual CueMender (Codex x TwitchCon) and VerifForge projects. This supplements AGENTS.md and the execution board. It does not activate their historical workers, budgets, schedules, permissions, or product requirements.

## Roles and assignments

Codex main owns the plan, shared contracts, task release, integration, acceptance and GitHub. Sol 6.1 Medium implements assigned Codex scopes; separate Sol 6.1 High reviewers inspect actual artifacts. DeepSeek Harness performs user-launched implementation, diagnosis, correction and qualification packets. DeepSeek is a substantive development participant, separate from the DeepSeek model later evaluated by the benchmark. Terra High handles any assigned computer use.

Current DeepSeek implementation: P1-CACHE. Reserved next implementation: P4-REPORT once records and sample inputs are stable. Bounded integrated qualification/reproduction work may be assigned to DeepSeek under P4.3/P5.3 when their prerequisites exist; the packet must specify exact commands, resources and any allowed operation. No future packet runs merely because its plan exists. Main retains the campaign budget and publication decisions.

One writer per path and one owner per operation. Disjoint work can proceed concurrently; overlapping work requires an explicit stopped-owner transfer or isolated checkout. Main does not switch shared branches or alter active pinned inputs underneath a worker. Control files are advisory records, not filesystem locks.

## Packet and handoff cycle

1. Main releases one coherent task: phase/subphase and stable subtask IDs, objective, current byte/commit baseline, dependencies, exact editable paths, protected files, known failure and prior evidence, acceptance criteria, command/resource limits and delivery paths. Small dependent steps stay in the same packet.
2. Main posts the complete populated launch/correction prompt in chat and saves the identical prompt in the packet. User launches it, normally in the stopped domain's existing DeepSeek chat. No placeholder reconstruction is left to the user.
3. Worker verifies current assignment and relevant pins, then diagnoses and implements within scope. Ordinary technical choices do not need another relay. A changed shared contract, unavailable prerequisite or unknown operation settlement is reported precisely. Independent in-scope work can continue.
4. Worker runs meaningful checks, records failures and actual outcomes, writes a report and manifest, settles owned processes and stops editing. The report maps each criterion/finding to code and evidence. The pasted return can be short because the shared artifacts hold the detail.
5. Main verifies artifact identity. An independent Sol High reviewer examines actual changed behavior and issues one consolidated review. Reuse valid existing evidence; additional execution must resolve a particular uncertainty or changed input.
6. If changes are required, main issues one finite correction packet with all actionable findings and retest expectations. Preserve closed findings and earlier failed evidence. Do not reopen unrelated accepted areas.
7. If accepted, main integrates the exact files, verifies any integration-specific uncertainty and records the narrow acceptance. Main advances eligible work and the scoped GitHub lifecycle without waiting for unrelated final/live gates.

## Avoiding handoff and review loops

Use a specific failure -> discriminating diagnostic -> supported correction -> decisive check. Do not repeat an unchanged failure or a passing broad suite without a reason. After two unproductive correction cycles, main changes the diagnostic approach or explicitly transfers the finite blocker to Codex Sol High. A narrow integration fix can also be Codex-owned after the prior writer is confirmed stopped and ownership is recorded. Implementation by a reviewer does not remain independent review; use a separate reviewer for that changed code.

A tool approval wait or environment denial is an operational blocker, not proof that the implementation is defective. Track unknown launch/exit state explicitly. Do not silently start a replacement operation when the prior operation may still be running.

## Evidence, publication and continuity

Track source implemented, integrated, independently reviewed, and actual operational acceptance separately. Local controls, mocked transport, replay and real provider results keep distinct labels. Partial source acceptance never means the complete benchmark is finished.

Main publishes accepted coherent source to the authorized public desanv01/FollowThrough repository. Bootstrap can be a baseline commit; later changes normally use focused branches/PRs, current-revision CI where configured, and reviewed merges. Keep private coordination, credentials and unrestricted traces out of public changes. A cache correction does not prevent publishing independently accepted components. Final hackathon submission remains a separate action.

Maintain the execution board, canonical state and worker registry when state changes. Preserve history as revisioned receipts; current controls must clearly state the present assignment rather than leave obsolete READY/RUNNING labels as the only visible status. No task-watching automation is created.
